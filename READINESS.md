# Booking and missed-call recovery

This branch adds application support. It does not activate a database, phone number, provider routing, SMS delivery, or production deployment. The `/book/demo` route remains entirely local sample state; it never calls booking APIs or phone providers. `/demo/intel-lock` and `/embed-demo` embed that sample.

## Architecture

Use an approved PostgreSQL database through `pg` with a pooled, TLS-verified connection string. Any compatible managed PostgreSQL can be used. Stripe Directory lookup confirmed Neon/Supabase/PostgreSQL options and Twilio; no provider was provisioned. Twilio's Stripe provisioning listing is a private beta unsuitable for real customer data, so activation should use an approved standard Twilio account instead.

Apply `db/001-booking.sql` once, using an approved migration owner (`npm run db:migrate`). No runtime auto-migration occurs. Use a least-privileged application database connection after migration. Tables must not be exposed through a public database REST API. The application has no client database credentials. Every public query scopes by business; service/resource relationships have composite business foreign keys. Global operators use the existing `ADMIN_PASSWORD` authentication. There are no self-service tenant logins, and operators must not share this credential with customers.

Booking and configuration writes lock the business row before checking capacity. A database trigger also guards overlapping confirmed bookings per technician. Transactions use PostgreSQL READ COMMITTED with the business row lock acquired before availability reads. Idempotency keys are scoped to the business, and a repeat key must match the original normalized request. Cancellation tokens are HMAC-derived and only hashes are stored. Customer management URLs carry tokens in the fragment, not request URLs; management APIs accept them in POST bodies. No customer PII is returned by public availability or management endpoints. Tokens should be treated as private access links.

Availability is explicit dated technician windows. Operators enter local times in an IANA timezone; skipped/ambiguous DST times are rejected. Storage uses UTC instants. Service duration, one-hour lead time, 60-day horizon, configured ZIP codes, and overlap checks are enforced server-side. This is ZIP validation, not geocoding or travel/parts/skills validation. Cancel then rebook is supported; no automated rescheduling, external calendar synchronization, notifications, or reminders exist.

## Activation gates and approvals

1. Approve the production code/deployment separately. Neither draft PR is publication approval.
2. Approve an existing or new managed PostgreSQL database, costs/terms if applicable, and the migration. Put `DATABASE_URL`, an operator-supplied secret of at least 32 characters as `BOOKING_TOKEN_SECRET`, and the exact canonical `APP_ORIGIN` into the secret store. Do not disable TLS verification. Set `BOOKING_ENABLED=true` only after database checks. Use a separate synthetic-data preview database; never point previews or tests at production.
3. In `/admin/booking`, create business name/slug/timezone/ZIP codes, services and durations, technicians, and availability. Keep the business paused until ready, then enable booking. Public pages stay inactive if either global or business booking is disabled. Customers can still cancel a saved booking while new bookings are paused.
4. Approve provider account/number/costs, public number ownership/forwarding, SMS registration and consent/opt-out setup. The application does not buy numbers, change provider settings, or create credentials. Configure provider credentials in the secret store. Set `PHONE_ROUTING_ENABLED=true` only after routing verification. Set `SMS_ENABLED=true` only after the approved message-delivery test. Never set live routing/SMS flags in preview.
5. Map the Twilio inbound SMS/voice number and a **different** forwarding number to one business, record the approved consent/support notice, and verify routing. Set its `routingVerified` and `smsEnabled` only after approval and successful tests. Configure number webhooks as POST:
   - Voice: `APP_ORIGIN/api/telephony/inbound`.
   - Incoming SMS: `APP_ORIGIN/api/telephony/sms-inbound`.
   - `<Gather>` consent and `<Dial>` result URLs are generated by the application.
   - Outbound SMS delivery callbacks are generated with the outbox ID.
6. Configure provider opt-out handling (Advanced Opt-Out if using a Messaging Service, otherwise verified standard number keyword handling). Twilio processes STOP/START responses; the application returns empty messaging TwiML and mirrors opt-outs locally. Obtain approved test recipients and explicit approval before placing calls or sending texts. Verify answered/no-answer/busy cases, affirmative consent, no consent, STOP/START, duplicate delivery, and delivery failure on the actual routing. Voicemail is an answered call and does not trigger recovery. Anonymous, withheld, SIP and other non-E.164 caller IDs are forwarded directly without an SMS consent prompt; they cannot create SMS consent or recovery messages.

Consent is explicit press-1 permission for one booking-link text if the call is missed. Calling by itself is not permission. Booking-checkbox consent does not bypass call-specific permission. The message identifies the business and includes STOP instructions. Contact opt-outs block new sends, including after another voice opt-in; START must restore consent. A caller receives at most one attempted recovery text per business per 24 hours, and each business is capped at 100 attempts per day. Limits include failed/uncertain attempts.

## Failure operations

Signed provider callbacks are checked against the configured canonical origin and expected account, with duplicate form fields rejected. Call/SMS identifiers and business/recipient mapping are checked. Callback replay is deduplicated durably. Missed-call processing queues one outbox row per call. The sender claims the row before calling the provider, then rechecks activation/consent under the business lock. Provider calls time out after 10 seconds, and SDK auto-retry is disabled. A timeout/crash can leave `unknown` or `sending`; no automated retries occur because the provider may already have accepted the SMS. Reconcile the provider log before any manual resend. The operator UI shows states and sanitized numeric error codes, never provider exception messages or message bodies. A signed status callback may reconcile accepted/uncertain delivery. Database outages return 503 so provider retry/fallback can be used; configure a provider failover route before activation.

Monitor stale pending/sending/unknown messages in `/admin/booking` and Vercel/provider operational logs. There is no background delivery worker: callbacks dispatch synchronously. Pending messages after interruption can be reconciled by the operator; replaying the same approved signed dial callback can dispatch a pending row, but cannot resend a claimed row. Never replay old callbacks with live credentials just to test.

Public API rate limits use persistent atomic counters, hashed platform-verified IPs (a shared fallback bucket outside Vercel), a hidden honeypot, bounded bodies, and server validation. This is a baseline, not bot verification. Monitor abuse; do not enable paid recovery without provider spend controls. Define a business-approved customer-data retention/deletion policy before real traffic. Periodically prune expired rate-limit rows and old webhook events in a reviewed maintenance job; retain call/outbox dedup records for the provider replay window. No retention job runs automatically.

## Verification

`npm test` uses an isolated in-memory PostgreSQL engine (PGlite) and fake SMS senders. It never connects to a hosted database, sends SMS, or places calls. Tests exercise lifecycle, idempotency, overlaps/concurrency, tenant boundaries, timezone/DST, authentication/origin checks, signed callbacks, replay, consent, opt-outs, rate limits, and uncertain delivery. The same suite can target an isolated loopback PostgreSQL server through TEST_DATABASE_URL; non-loopback hosts are rejected. Local native PostgreSQL contention and the real browser/API lifecycle were also verified with synthetic data. Hosted staging database behavior and actual provider routing still require approved activation checks. `npm run typecheck` and `npm run build` must pass. Desktop/mobile browser checks use synthetic data only. Regression coverage includes signed anonymous-caller routes and overnight appointments with next-day conflicts and alternate technicians.

Calendar sync, email/SMS reminders, abandoned-booking recovery, deposits, analytics, route-aware scheduling, multiple locations, advanced automation, priority support and paid-plan limits are not implemented. `/readiness` documents this explicitly.
